# 装置ごとの学習ベース異常検知（Autoencoder）

`tools/anomaly_autoencoder.py`

## これは何か

`tools/ai_grafana_autopilot.py` の `AnomalyDetector` は
「CPU使用率 >= 80%」のような**全装置共通の固定閾値**で異常を判定する。
これは分かりやすい反面、装置ごとの「普段」を無視してしまう。
普段CPUが10〜25%で推移しているアクセススイッチが55%に張り付いても、
80%という閾値を下回っているのでルールベースでは検知できない。

このモジュールは装置ごとに小さなAutoencoder（入力を一度圧縮してから
復元するニューラルネット）を学習し、**その装置の正常な状態の復元誤差は
小さく、学習していない未知のパターンの復元誤差は大きくなる**という
性質を使って「その装置にとっての普段と違う」を検知する。

固定閾値のルールベースを置き換えるものではなく、
補完する位置づけ（`ai_grafana_autopilot.py`にはまだ統合していない。
統合する場合は装置ごとに十分な学習データが溜まるまでの立ち上がり
期間の扱いを別途設計する必要がある）。

## なぜPyTorchを使っていないか

このサンドボックス環境で実際に試した結果：

- 通常の `pip install torch` はLinux向けにCUDA対応版を解決し、
  `nvidia-cudnn`・`cuda-toolkit` など**数GB規模の依存**を追加でダウン
  ロードしようとし、実際にディスク容量不足でインストールが失敗した
  （このセッションの残りディスクは2〜3GB程度）。
- CPU専用ビルドは `download.pytorch.org` の専用インデックスからしか
  取得できないが、このサンドボックスのegressポリシーでブロックされて
  いる（403）。
- `--no-deps` でtorch本体だけ入れても、`import torch` の時点で
  `libcudart.so` 等のCUDA共有ライブラリを探しに行って失敗する
  （近年のtorchはCPU/GPUでパッケージが分かれておらず、CUDA前提の
  読み込み処理が`import`時に走る）。

そのため、依存を増やさない・環境の制約に合わせるという2つの理由から、
Autoencoderの前方伝播・誤差逆伝播（バッチ勾配降下）を**NumPyのみで
手書き**した。1隠れ層・活性化tanh・出力層は線形・損失はMSEという
最小構成で、フレームワークが無くても手で書ける規模に抑えている。

## 使い方

```python
from tools.anomaly_autoencoder import DeviceAnomalyModel

# 装置の「正常」な履歴（CPU%、区間あたりの通信量）を集める
normal_samples = [(cpu, bytes_per_interval), ...]

model = DeviceAnomalyModel(seed=1)
model.fit(normal_samples, epochs=400, lr=0.1, threshold_k=4.0)

model.is_anomaly(cpu_percent=55.0, bytes_per_interval=2200.0)  # -> True/False
model.score(cpu_percent=55.0, bytes_per_interval=2200.0)       # 復元誤差(float)
```

`threshold_k` は「学習データの復元誤差の平均 + threshold_k × 標準偏差」
を異常判定の閾値にする係数。大きいほど普段のブレを誤検知しにくくなる
代わりに、小さな異常を見逃しやすくなる（デフォルト4.0）。

## 実行例（`python3 tools/anomaly_autoencoder.py`）

普段CPU 8〜25%で推移し、通信量がCPUにゆるく相関する装置を想定した
デモ。200サンプルで学習し、4パターンを判定させた実際の出力：

```
学習: loss 0.19030 -> 0.00022
異常判定の閾値(復元誤差): 0.001366

✅ 正常  正常 (CPU=18%, 通常トラフィック)  復元誤差=0.000208
🚨 異常  ルールベースなら見逃す異常 (CPU=55%, 80%閾値未満)  復元誤差=0.084606
🚨 異常  明白な異常 (CPU=95%)  復元誤差=0.277213
🚨 異常  CPUは正常域だが通信量だけ異常  復元誤差=0.070109
```

固定閾値（80%）では絶対に引っかからない「CPU 55%」のケースが、
この装置にとっては明らかに異常な水準として正しく検知されている。
また「CPUは正常域だが通信量だけ跳ねている」ケースも、CPUと通信量の
相関パターンが学習データと異なることから検知できている。

## 装置ごとに学習内容が変わることの確認

`tests/test_anomaly_autoencoder.py::test_different_devices_learn_different_baselines`
で固定している通り、普段CPU 45〜65%で稼働するコアスイッチのような
装置を学習させると、同じ「CPU 55%」は異常と判定されない
（アクセススイッチのモデルでは異常と判定される）。
装置の役割ごとに閾値を変える設定を人手で書く必要がなく、
履歴データから自動でその装置の「普段」を学習する点が
固定閾値ルールとの違い。

## テスト

```bash
pytest tests/test_anomaly_autoencoder.py -v
# 9/9 成功
```

固定している内容：
1. 勾配降下で実際に損失が減ること
2. 学習データが少なすぎる場合はエラーになること（最低4サンプル）
3. 正常なサンプルの復元誤差が閾値を超えないこと
4. **ルールベースの固定閾値(80%)を下回る中程度の異常が検知できること**
   （このモジュールの存在意義そのもの）
5. 明白な異常（95%）も検知できること
6. CPUは正常域でも通信量だけが異常なパターンを検知できること
7. 異常度が「普段からの逸脱の大きさ」に対して単調に増加すること
8. `fit()`前に`score()`を呼ぶとエラーになること
9. 装置ごとに学習した「正常」の基準が異なること

## 制約・今後の拡張余地

- `ai_grafana_autopilot.py` への統合は未実施。統合する場合、
  装置追加直後で学習データが無い期間の扱い（何もしない／
  ルールベースのみで代替する等）を設計する必要がある
- 特徴量はCPU%と通信量の2次元のみ。インターフェース数が多い装置の
  ポートごとの異常や、時系列の「変化の速さ」（フラップ検知は
  既存のルールベースが別途担当）は扱っていない
- 学習はバッチ勾配降下を固定エポック数まわすだけで、収束判定や
  early stoppingは無い
- 永続化していない。プロセスが落ちれば学習した重みも消える
  （装置起動のたびに履歴が溜まってから学習し直す想定）
