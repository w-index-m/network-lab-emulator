# Catalyst 3650 モデル駆動API連携（RESTCONF / NETCONF）設計メモ

netmiko(CLI-over-SSH) の上位互換として、実機3650(IOS-XE 16.x) の
**RESTCONF / NETCONF** で構造化データによる投入・検証を行うための設計メモ。
実装はまだ。まず対応モデル・エンドポイント・組み込み方針を固める。

---

## 1. 前提（バージョン / ライセンス）

- RESTCONF/NETCONF は **IOS-XE 16.3 以降**でほぼ利用可（3650は Denali/Everest/Fuji 16.x）。
- ライセンスは **IP Base 以上**が無難。Lite/LAN Baseだと機能制限に注意。
- gNMI は版が新しめのIOS-XEのみ → 3650では版次第。まずは RESTCONF を主軸に。

## 2. 有効化（実機で一度だけ）

```
configure terminal
 aaa new-model
 aaa authentication login default local
 aaa authorization exec default local
 username admin privilege 15 secret cisco
 ip http secure-server        ! RESTCONF は HTTPS(443)
 restconf                     ! RESTCONF 有効化
 netconf-yang                 ! NETCONF(830) 有効化
end
write memory
```
- 疎通確認: `GET https://<host>/restconf/data/Cisco-IOS-XE-native:native/hostname`

## 3. RESTCONF エンドポイント設計

- ベースURL: `https://<host>/restconf/data/<model>:<container>[/<key>=<val>]`
- ヘッダ: `Accept: application/yang-data+json` / `Content-Type: application/yang-data+json`
- 認証: HTTP Basic（`admin:cisco`）。TLSは自己署名なので検証OFF（`verify=False`）想定。
- メソッド: `GET`(取得) / `PATCH`(マージ投入) / `PUT`(置換) / `DELETE`。

### 3.1 設定投入（config models）

| 対象 | モデル / パス | 備考 |
|---|---|---|
| ホスト名 | `Cisco-IOS-XE-native:native/hostname` | |
| インターフェース | `Cisco-IOS-XE-native:native/interface/GigabitEthernet=1%2F0%2F1` | `/` は `%2F` エスケープ |
| VLAN | `Cisco-IOS-XE-native:native/vlan` | `vlan-list` |
| SVI/IP | `.../interface/Vlan=10/ip/address/primary` | |
| OSPF | `Cisco-IOS-XE-native:native/router/router-ospf` | `Cisco-IOS-XE-ospf` 拡張 |
| ip routing | `Cisco-IOS-XE-native:native/ip/routing` | L3化 |

投入例（SVI Vlan10 に IP、PATCH）:
```json
PATCH .../native/interface/Vlan=10
{
  "Cisco-IOS-XE-native:Vlan": {
    "name": 10,
    "ip": { "address": { "primary": { "address": "10.10.10.1", "mask": "255.255.255.0" } } }
  }
}
```

> 注: `native` ツリーはCLIとほぼ1:1なので、**既存の running-config を native JSON へ機械変換**すれば
> 投入器を作れる。ただしマッピング表の整備が重いため、投入は当面 netmiko(CLI) を推奨。

### 3.2 検証（operational state models）← ここがAPI化の主目的

CLI grep より堅い。状態を構造で取得して判定する。

| 見たい状態 | oper モデル | 判定キー |
|---|---|---|
| OSPF 隣接 | `Cisco-IOS-XE-ospf-oper:ospf-oper-data` | `.../ospf-neighbor/adjacency-state == "full"` |
| ルート | `Cisco-IOS-XE-routing-oper` / `ietf-routing:routing-state` | プロトコル別 prefix |
| インターフェース | `Cisco-IOS-XE-interfaces-oper:interfaces/interface` | `oper-status == "if-oper-state-ready"` |
| STP | `Cisco-IOS-XE-spanning-tree-oper:stp-oper-data` | root bridge / port role=`stp-port-role-alternate`(BLK相当) |

検証例（OSPF全隣接がfullか）:
```
GET https://<host>/restconf/data/Cisco-IOS-XE-ospf-oper:ospf-oper-data
→ JSON中の全 ospf-neighbor.adjacency-state を走査し、full 以外があればFAIL
```

## 4. 既存ツールへの組み込み方針

`tools/eveng_deploy.py` に **`--transport {ssh,restconf,netconf}`** を追加する構成:

```
verify --transport ssh       → 現行: netmiko で show + 文字列 expect（既存）
verify --transport restconf  → requests で oper GET + JSONPath 判定（新規）
deploy --transport restconf  → native JSON を PATCH（将来。まずはssh）
```

- `checks.json` を拡張し、`ssh` は `{cmd, expect}`、`restconf` は
  `{path, jsonpath, equals}` の2形式を許容する。
- 依存: RESTCONF=`requests` のみ（軽い）。NETCONF=`ncclient`（やや重い）。
- TLSは自己署名前提で `verify=False`（社内ラボ限定。運用では要CA）。

### 提案する段階導入
1. **フェーズ1**: RESTCONF **verify** を追加（OSPF/インターフェース/STPのoper判定）。投入はnetmikoのまま。
2. **フェーズ2**: STPのport-role判定・ルート確認を足し、`checks` をSSH/RESTCONF両対応に。
3. **フェーズ3**: 必要なら native JSON による RESTCONF **deploy**（VLAN/SVI/OSPFなど代表項目から）。

## 5. リスク / 留意点

- **モデル名・パスはIOS-XE版で差異**あり。実機で `?` (RESTCONF root) や
  `GET /restconf/data/ietf-yang-library:modules-state` を叩いて**搭載モデルを確認**してから固める。
- native投入はCLIと等価だが**構造化ゆえの落とし穴**（キー順・必須leaf）があるため、
  代表項目に絞って段階的に。
- 認証・TLSは社内ラボ用の簡略前提。外に出すならCA・アカウント分離が必要。
- この本ツール自身(擬似CLI)は RESTCONF/NETCONF を**話さない**。連携はあくまで
  「本ツールで設計 → 実機3650へAPI投入/取得」という外部ツール(eveng_deploy.py)経由。
